# Повседневные инциденты Kafka

Раздел тренирует последовательность **наблюдение -> гипотеза -> исправление -> проверка**. Это детерминированная учебная модель: действия изменяют рассчитанное состояние и кадры визуализации, но не создают отказов в настоящем Docker-стенде. Реальная лаборатория Kafka находится отдельно.

## Шесть сценариев

| Инцидент             | Что нужно заметить                                                            | Что считать результатом                                                                                               |
| -------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Рост lag             | База downstream обрабатывает медленнее входа; партиции назначены корректно    | Скорость и возраст стабилизированы, backlog разобран, заказы действительно записаны                                   |
| Poison pill          | Ошибка воспроизводится на одной координате из-за нарушения контракта          | Исходная запись сохранена в карантине с причиной, партиция продолжает работу, разбор карантина остаётся явной задачей |
| advertised.listeners | Bootstrap доступен, а объявленный в metadata адрес недоступен из сети клиента | Metadata, подтверждённая запись и чтение проверены из проблемной сети                                                 |
| Недостаточный ISR    | RF=3, minISR=2, ISR=1, acks=all                                               | Follower догнали leader, ISR восстановлен, запись подтверждена при исходной гарантии                                  |
| Заполненный диск     | Ёмкости не хватает для согласованной истории                                  | Старые данные доступны, новые записываются, репликация здорова и есть запас ёмкости                                   |
| Повторное списание   | Внешний платёж завершился раньше сбоя до commit                               | Повтор eventId не создаёт нового списания, прежние дубли сверены и компенсированы                                     |

Числа в каждом кейсе - учебные исходные условия. Это не результаты измерения реального Kafka-кластера. `duplicates` означает число неурегулированных лишних списаний: компенсация уменьшает его, сохраняя историю операций.

## Как начисляется завершение

1. Собрать минимум два **разных** наблюдения. Повтор одного наблюдения не создаёт новых свидетельств.
2. Выбрать гипотезу, которая объясняет наблюдения. Неверная гипотеза получает предметный разбор.
3. Выполнить подходящее исправление. Исправление изменяет состояние, но ещё не завершает кейс.
4. Явно проверить результат. Только после этого сервер выставляет `verified=true`.

Ранний вызов проверки не засчитывает кейс. Клиент передаёт только тип действия и идентификатор варианта; он не передаёт произвольное состояние, оценку или флаг успеха. Сервер использует своё сохранённое состояние. Владелец локального компьютера управляет исходниками и базой: это тренажёр для самостоятельного обучения, а не система защищённой аттестации.

Неверные решения показывают причинно связанные последствия. Например, сброс offset в конец уменьшает lag, но пропускает заказы; увеличение числа consumer усугубляет перегрузку базы; уменьшение minISR восстанавливает видимую запись ценой нарушения требования сохранности. Нажатие «проверить» не превращает такой результат в успех.

В модели заполненного диска ручное удаление сегментов и несогласованное сокращение retention уничтожают требуемую историю. После этого простой правильный параметр не восстанавливает данные. Для прохождения безопасного пути нужен сброс учебного кейса; в настоящей системе потребовалась бы отдельная процедура восстановления из доступного источника.

## Состояние и визуализация

Публичный каталог находится в [incidents.mjs](../content/incidents.mjs), правила переходов - в [incident-engine.mjs](../server/incident-engine.mjs). Каталог содержит названия доступных действий, симптомы и источники, но не серверные ключи правильных ответов.

Каждое принятое учебное действие создаёт кадр истории: текст, уровень сообщения, этап, значения метрик и состояние узлов `producer`, `broker`, `consumer`, `external`. Некорректные API-запросы отклоняются без изменения состояния. История хранит первый кадр и до 39 последних кадров, список наблюдений ограничен тремя уникальными значениями. Эти снимки позволяют воспроизвести изменение потока и вернуться к причинной связи между решением и последствием. После 40 кадров промежуточная часть истории сокращается, исходное состояние сохраняется.

```text
createIncidentState(id) -> первоначальное состояние
publicIncident(id) -> публичный каталог одного кейса
actIncident(id, persistedState, { action, choice? }) -> новое состояние
```

Разрешённые `action`: `observe`, `hypothesis`, `fix`, `verify`, `reset`. Для первых трёх `choice` является строковым идентификатором из каталога. Функция не изменяет переданное состояние, не читает часы и не использует случайность. Неправильные учебные решения возвращают объяснённое состояние; некорректный контракт запроса вызывает `INVALID_INCIDENT_INPUT`.

SQLite сохраняет состояние через общий сервер приложения. Сам engine остаётся чистой функцией, что позволяет независимо проверить переходы и повторно загрузить сериализованное состояние. Reset создаёт новый кейс и очищает его текущую учебную историю; он не меняет настоящий Kafka.

## Проверка

Тесты [incidents.test.mjs](../tests/incidents.test.mjs) проверяют все шесть полных цепочек и каждую неправильную гипотезу/исправление, преждевременное завершение, повтор одного наблюдения, неизменяемость входа, сохранение JSON, ограничение истории, повреждённое состояние и невозможность прислать клиентский балл. Отдельные проверки защищают от ложного успеха при нулевом lag, сокращённом ISR, неурегулированных списаниях и удалении истории.

```sh
node --test tests/incidents.test.mjs
```

Локальный запуск этой команды 07.10.2026 завершился результатом **21 passed, 0 failed**. Браузерная доступность, воспроизведение кадров и сохранение через HTTP проверяются отдельно от чистого engine. Этот результат не подтверждает публикацию репозитория или выполнение GitHub Actions; общие результаты поставки фиксируются в отдельном отчёте.

## Основания

Источники проверены 7 октября 2026 года:

- [Apache Kafka: Broker Configs](https://kafka.apache.org/42/configuration/broker-configs/) и [Listener Configuration](https://kafka.apache.org/42/security/listener-configuration/): адреса прослушивания и объявленные endpoints имеют разные задачи.
- [Confluent: Dead Letter Stream](https://developer.confluent.io/patterns/event-processing/dead-letter-stream/): отдельный поток сохраняет непригодную для обработки запись с контекстом для разбора. Возможность продолжения должна соответствовать бизнес-политике порядка и полноты.
- [Apache Kafka: Topic Configs](https://kafka.apache.org/42/configuration/topic-configs/): связь ISR, minISR и подтверждения записи.
- [Apache Kafka: Monitoring](https://kafka.apache.org/42/operations/monitoring/) и [Hardware and OS](https://kafka.apache.org/42/operations/hardware-and-os/): наблюдение состояния реплик и требований к хранению.
- [Apache Kafka: Design](https://kafka.apache.org/42/design/design/) и [Confluent: Transactions](https://developer.confluent.io/courses/architecture/transactions/): гарантии Kafka не распространяются автоматически на произвольные внешние эффекты.

Учебные числа, фабулы и последовательности решений разработаны для этого тренажёра; они не описывают реальный инцидент пользователя или компании.
