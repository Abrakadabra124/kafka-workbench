# Спецификация лаборатории 1.1

Дата: 2026-11-07. Локальный персональный продукт, без публичного исполнения пользовательского кода.

## Исследование и решения

- [Apache Kafka Docker](https://kafka.apache.org/42/getting-started/docker/): сохраняем официальный apache/kafka:4.2.2. Новый Compose project отделён от прежней одноброкерной лаборатории, без опубликованных портов, privileged и Docker socket внутри контейнера.
- [Операции и offsets](https://kafka.apache.org/42/operations/basic-kafka-operations/): committed offset указывает следующую запись. Нулевой lag сам по себе не доказывает обработку: verifier сопоставляет журнал отправки, реальные записи, чтения и committed offsets.
- [Producer](https://kafka.apache.org/42/configuration/producer-configs/): acks=all и idempotence; три реплики, min.insync.replicas=2. Один отключённый брокер оставляет возможность записи; результат подтверждается metadata и чтением.
- [Java Consumer API](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html): явный commit после обработки. Каждое чтение создаёт новый клиент, поэтому повтор без commit демонстрирует redelivery.

Сравнение вариантов: фиксированные CLI-команды сохраняются как базовая лаборатория; произвольный терминал требует ненужных для учебной цели полномочий; JSON-рецепт позволяет самостоятельно менять записи, partition, группу, лимит и commit с проверяемым контрактом. Java-клиент использует библиотеки установленной Kafka и не добавляет клиентскую npm-зависимость. Три совмещённых broker/controller узла подходят для выделенной лаборатории, но не служат production-рекомендацией.

## Контракт

Адаптер компилируется в multi-stage Docker build с официальным Eclipse Temurin 21 JDK; в конечный образ Kafka копируется только `.class`. Kafka и JDK закреплены digest в `labs/workspace.Dockerfile`. Это необходимо, поскольку runtime-образ Kafka не содержит `jdk.compiler`. Исходники сборки ограничены `labs/.dockerignore`. [Документация multi-stage](https://docs.docker.com/build/building/multi-stage/), [официальный Temurin](https://hub.docker.com/_/eclipse-temurin).

Три упражнения: доставка/commit, повтор без commit, отказ и восстановление. Подготовка выделяет topic и две группы внутри собственного Compose project. Рецепт содержит до 12 записей (partition 0..2, key и value), consumer group из allowlist, maxRecords 1..36 и commit boolean. JSON не исполняется как код. Все процессы запускаются без shell; конфигурация Docker и пути фиксированы сервером.

Запуск и оценка раздельны. Verifier заново читает topic независимо от учебной группы, сравнивает точные partition/offset/key/value, проверяет подтверждённое чтение всей серии и offsets группы, здоровые реплики. Для replay требуются два чтения одинаковых offsets без commit до финальной обработки; для recovery требуется наблюдавшийся отказ, успешная запись при отказе и восстановленный ISR.

SQLite сохраняет черновики и историю. Подготовка повторной попытки/сброс удаляет только topic и группы выбранного задания, сохраняя историю и прежнее обучение. Остановка всего нового стенда требует явного подтверждения и не затрагивает старую лабораторию.

Ошибочный JSON блокирует сохранение/подготовку/запись/чтение, но не препятствует инспекции, восстановлению и удалению стенда. Снимок показывается с временем измерения, после ошибки не объявляется новым. Движение записи существует только для успешного действия с фактически полученными записями.

## Визуализация и приёмка

CSS 3D: три стойки, партиции и роли leader/follower, producer и consumer group, связи и подтверждённые события. Снимок содержит время; он не называется непрерывной телеметрией. Воспроизведение записи помечено отдельно от текущей операции. Никаких случайных метрик, бесконечного потока в неподвижном снимке или выдуманных реплик. Доступен текстовый эквивалент.

Metadata сообщает состав ISR и общий end offset партиции, но не отдельный log end offset каждого follower. Ячейки синхронных реплик иллюстрируют общий журнал, не являются точной метрикой реплики. Для реплик вне ISR вместо такого заполнения показан `?`: после отключения нельзя приписывать им новые записи лидера.

Критерии: каждый новый сценарий проходит реальный путь, негативную проверку без зачёта, восстановление и повтор. Viewports 320/390/768/1440 без горизонтального переполнения; клавиатура, pause/reduced motion, невидимость/фон, console без ошибок; сохранение данных после рестарта; unit/integration/E2E/build и успешный GitHub CI. Доказательства публикуются после выполнения, не заранее.

64 GiB RAM на пользовательском Windows достаточно для ограниченных контейнеров (до 1.5 GiB каждый); Docker на момент ревизии выключен. Общий hardware lock обязателен для тяжёлых локальных запусков. Antigravity: ранее неустранённая ошибка авторизации, новый вызов не выполнялся.
