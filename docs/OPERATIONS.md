# Запуск и эксплуатация Kafka Workbench

Kafka Workbench рассчитан на одного учащегося на доверенном локальном компьютере. Сервер слушает `127.0.0.1`, интерфейс и API работают на одном origin. Учебный прогресс хранится на сервере в SQLite, а не только в браузере. Аккаунты и удалённый многопользовательский доступ в эту поставку не входят.

## Требования и установка из GitHub

Нужны Git, Node.js 24.19+ в ветке 24.x LTS и npm. LTS означает долгосрочную поддержку версии. Для настоящей лаборатории дополнительно нужен Docker Engine с Linux containers. На Windows подойдёт запущенный Docker Desktop. Без Docker доступны теория, проверка знаний и учебные модели; доступность настоящего брокера проверяется отдельно.

```sh
git clone https://github.com/Abrakadabra124/kafka-workbench.git
cd kafka-workbench
npm ci
npm run check
npm start
```

Откройте [Kafka Workbench](http://127.0.0.1:4184). Команда `npm ci` устанавливает версии из lockfile. `npm run check` выполняет проверки проекта и сборку интерфейса. Для обычной повторной сборки достаточно `npm run build`.

GitHub хранит исходники и выполняет автоматические проверки. Приложение и брокер запускаются на вашем компьютере. GitHub Pages не запускает Node.js API, SQLite или Kafka. Конфигурация публичного хостинга и Codespaces в поставку не включена: текущий сервер намеренно принимает только локальные Host и Origin. Не отключайте эти проверки для перенаправления порта.

## Windows

Дважды нажмите `Start-Kafka-Workbench.cmd` или выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1
```

Скрипт найдёт Node.js 24, установит зависимости, соберёт интерфейс, запустит сервер в скрытом окне, проверит HTTP health и принадлежность порта запущенному процессу, затем откроет браузер. Он умеет использовать уже установленный runtime Codex, если системный Node слишком старый. Системный Node и глобальная политика PowerShell не изменяются.

Можно явно указать совместимый runtime:

```powershell
$env:KAFKA_WORKBENCH_NODE = 'C:/tools/node24/node.exe'
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1 -NoBrowser
```

Для другого свободного порта передайте `-Port 4186`. Один checkout запускается скриптом в одном экземпляре; перед сменой порта остановите предыдущий процесс. Повторный запуск уже работающего экземпляра открывает его, не запускает вторую копию и не изменяет данные.

Остановка:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stop.ps1
```

Есть также `Stop-Kafka-Workbench.cmd`. Скрипт сверяет PID, путь Node, путь серверного файла и время создания процесса. Он останавливает только свой экземпляр. Данные и лабораторные контейнеры сохраняются. Если сервер запускался вручную через `npm start`, завершите его в соответствующем терминале сочетанием Ctrl+C.

## Linux и macOS

После установки и сборки запускайте `npm start` в терминале. Ctrl+C останавливает приложение. Для другого порта:

```sh
PORT=4186 npm start
```

## Настоящая лаборатория Kafka

Перед запуском лаборатории убедитесь, что Docker доступен:

```sh
docker info
```

Откройте лабораторию в интерфейсе и запустите стенд. Используется фиксированная версия `apache/kafka:4.2.2`. Первый запуск требует доступа к registry и времени на загрузку образа. Версионный тег фиксирует выбранный выпуск, но не является неизменяемым digest.

Управление стендом выполняется через предусмотренные действия приложения. Не отправляйте произвольные команды Docker из браузера. Учебные метрики симулятора и ответы настоящего брокера имеют разный смысл; завершение модели не доказывает выполнение настоящего эксперимента.

Завершите лабораторию средствами интерфейса, пока приложение ещё работает. Действие остановки стенда удаляет его контейнер и учебные сообщения; прогресс уроков и расследований остаётся в SQLite. Остановка Node.js сама по себе не останавливает Docker. Не используйте `docker system prune`, массовое удаление контейнеров или томов для очистки учебного стенда: они могут затронуть другие проекты.

У настоящей лаборатории одно имя Compose-проекта: `kafka-workbench-lab`. Несколько checkout на разных HTTP-портах не создают независимые брокеры. Перед действием runner проверяет метку с путём Compose-файла: если существующий контейнер создан другим checkout, операция прекращается без изменения контейнера. Управляйте таким стендом из исходного checkout. Для запуска лаборатории из новой копии сначала завершите прежний стенд из его приложения. Внутри одного приложения одновременно выполняется одна операция стенда.

## Данные и резервное копирование

Основная база: `data/learning.sqlite`. Папка `data/` содержит локальные данные и журналы и не должна публиковаться в Git. При ручном запуске можно выбрать другой каталог через переменную `DATA_DIR`; Windows launcher использует каталог `data` своего checkout.

Консервативная резервная копия выполняется при остановленном сервере:

1. Завершите текущую лабораторную операцию.
2. Остановите приложение и убедитесь, что его процесс завершился.
3. Скопируйте весь каталог `data` в отдельный приватный каталог с новой датой. Сохраняйте вместе SQLite и возможные файлы `-wal` и `-shm`.
4. Запустите приложение и проверьте прежний прогресс.

Не копируйте только `learning.sqlite` во время работы: SQLite может хранить свежие записи в журнале WAL, то есть write-ahead log. Экспорт прогресса из интерфейса полезен для чтения и переноса отчёта, но не заменяет полную резервную копию базы.

Восстанавливайте сначала отдельный экземпляр: клонируйте ту же версию исходников в новый каталог, установите зависимости, скопируйте резервную копию в его `data`, соберите приложение и запустите на другом порту. Проверьте уроки, результаты, заметки и историю расследований. Не запускайте две копии приложения с одной базой. Файлы `server-process.json`, `server-process.pending.json` и журналы из копии не нужны новому экземпляру; не переносите их, чтобы launcher не принимал старую запись процесса за свою. На этой проверке не запускайте настоящую лабораторию из восстановленной копии: её Compose-проект общий с основным экземпляром, а принадлежность контейнеров защищена описанной выше проверкой.

Копия учебного прогресса не является резервной копией данных Kafka. Брокер и его журналы имеют отдельный жизненный цикл. Восстановление SQLite не откатывает offsets или записи в Kafka.

## Диагностика

```sh
curl http://127.0.0.1:4184/api/health
```

Ожидаемый ответ приложения содержит `"ok": true`. Этот endpoint подтверждает доступность API, но не подтверждает состояние брокера. Для лаборатории используйте её собственные результаты и фактические ответы Kafka.

На Windows launcher пишет stdout в `data/server.log`, stderr в `data/server-error.log`. При ошибке запуска сначала прочитайте stderr. Если порт занят, выберите другой порт или остановите известный вам процесс. Не завершайте все процессы Node или Docker.

Если скрипт сообщает о несовпадении личности процесса, он специально прекращает работу. Проверьте запись `data/server-process.json` и соответствующий процесс вручную. Не обходите проверку массовым завершением процессов.

## Автоматические проверки

```sh
npm ci
npm run check
npm audit --audit-level=high
npx playwright install chromium
npm run test:e2e
```

Реальная Kafka-проверка требует запущенного Docker. Она использует отдельный Compose-проект `kafka-workbench-lab-test` и очищает его после проверки, не используя имя пользовательского стенда. Не запускайте несколько таких тестов одновременно на одном Docker Engine. На Linux/macOS:

```sh
RUN_LIVE_LABS=1 node --test tests/labs.test.mjs
```

В PowerShell:

```powershell
$env:RUN_LIVE_LABS = '1'
node --test tests/labs.test.mjs
Remove-Item Env:RUN_LIVE_LABS
```

Workflow `.github/workflows/ci.yml` выполняет проверки и сборку на Windows и Linux. Отдельное Linux-задание запускает браузер и настоящий брокер. Права workflow ограничены чтением репозитория, действия закреплены commit SHA, browser failure artifacts хранятся семь дней. Наличие workflow не доказывает успешного выполнения: результат конкретного запуска проверяйте во вкладке Actions.

## Обновление и откат

Перед обновлением остановите приложение и сделайте копию данных. Получите выбранную версию, выполните `npm ci`, `npm run check`, затем запустите приложение и проверьте сохранённый прогресс. Версия исходников и база должны быть совместимы. Для отката безопаснее запустить прежнюю версию с соответствующей копией данных в новом каталоге, чем заменять файлы работающего экземпляра.

Локальный режим не имеет границ изоляции публичного SaaS. Для удалённого сервиса потребуются аутентификация, TLS, отдельные исполнители лабораторий, разграничение данных и проверенные эксплуатационные процедуры. Текущая поставка не заявляет такие возможности или результаты нагрузочных испытаний.
