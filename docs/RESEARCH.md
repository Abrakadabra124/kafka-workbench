# Kafka Workbench: исследование и критерии качества

Дата проверки источников: **7 октября 2026 года**. Исследование выполнено по открытым первичным материалам Apache Kafka, Confluent Developer, Redpanda University и GitHub Docs. Локальные проекты сравнены по README без изменения их файлов. Это обзор подходов и проектные решения, а не независимый аудит всех конкурентов и не доказательство достижения «уровня бигтех».

## Цель и границы

Создать воспроизводимый русскоязычный тренажёр, исходники которого можно получить с GitHub и запустить на личном компьютере. Пользователь должен объяснить базовые гарантии Kafka, принять инженерное решение, увидеть последствия в модели и выполнить ограниченный эксперимент с настоящим брокером.

«Уровень бигтех» переводится в проверяемые свойства: точность материала, понятная обратная связь, доступность интерфейса, воспроизводимый запуск, автоматические проверки, безопасные ограничения и явные свидетельства результата. Брендовая формулировка не заменяет нагрузочные испытания, исследование с пользователями, внешний аудит или опыт эксплуатации.

Поставка рассчитана на одного учащегося на доверенном локальном компьютере. Настоящая лаборатория использует **apache/kafka:4.2.2** в KRaft и один брокер. Явный версионный тег фиксирует выбранный выпуск, но не является неизменяемым digest и не доказывает побайтовую воспроизводимость. Версия не обозначается как последняя. Документация 4.2 уже помечена сайтом как предыдущая, а страница Quick Start обновлена 29 сентября 2026 года и показывает образ 4.2.2. Обновление версии требует повторной проверки стенда. [Apache Kafka Quick Start 4.2](https://kafka.apache.org/42/getting-started/quickstart/).

## Принятые продуктовые решения

1. **Персональное обучение без регистрации.** Уровень доверия - один локальный пользователь. Прогресс хранится сервером в SQLite, встроенной реляционной базе. Аккаунт не добавляет полезной изоляции на одном доверенном компьютере, но создаёт лишний шаг и обязательства по восстановлению доступа. Публичная многопользовательская версия требует отдельного проекта безопасности.
2. **Сначала модель, затем наблюдение.** Учебная визуализация даёт управляемые состояния и быстрый разбор причин. Реальная лаборатория получает ответы Apache Kafka. Их результаты подписываются отдельно; анимация не служит свидетельством записи на брокере.
3. **Серверная оценка ответа.** Клиент отправляет выбор, сервер сверяет его с учебным ключом и сохраняет результат. Клиент не назначает собственный балл. Это защита целостности обычного интерфейса, а не защищённый экзамен: владелец локального компьютера управляет исходниками и данными.
4. **Небольшая цельная программа.** Шесть модулей по три урока: основы, producer, consumer, надёжность, эксплуатация и архитектура. Каждый урок имеет проверяемую цель, три объясняющих блока, выводы, вопрос, ситуацию и источники. Указанная длительность - редакторская оценка, а не измеренная статистика учащихся.
5. **Проверка понимания через ситуацию.** После определения offset нужно выбрать точку commit, после replication - предсказать результат потери ISR. Повторение ошибочных решений предпочтительнее увеличения процента за просмотр. Это проектная учебная гипотеза; её эффективность требует пользовательского исследования.
6. **Один broker для доступного старта.** Совмещённые роли broker/controller сокращают локальные требования. Высокая доступность, отказ узла, восстановление реплик и деградация кворума остаются теорией и моделью. Apache Kafka рекомендует избегать combined mode для критичных сред. [KRaft](https://kafka.apache.org/42/operations/kraft/).
7. **Фиксированные действия лаборатории.** Вызовы с разрешёнными параметрами легче проверить и ограничить, чем произвольный shell или произвольный код. Результат должен включать фактические topic, partition, offset и записи, когда они доступны. Ошибка запуска должна быть показана как ошибка, без выдачи симуляции за реальное выполнение.
8. **GitHub как исходники и автоматическая проверка.** CI, Continuous Integration, означает автоматические проверки изменений. Сборка, тесты и лабораторный smoke проверяют разные свойства. Наличие YAML не доказывает успешный запуск на GitHub; нужны ссылка на run и его итог. Actions закрепляются полным SHA, права токена ограничиваются необходимыми. [GitHub: Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).

## Технические ловушки, которые материал должен исключать

| Тема                     | Корректная граница                                                                                                                                | Учебная проверка                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Offset                   | Принадлежит партиции; committed offset задаёт точку продолжения. Получение через poll не равно завершению обработки. Числа могут иметь промежутки | После обработки 0-4 следующая позиция 5; при незавершённой записи нельзя фиксировать дальнейшее завершение |
| Lag                      | В простой модели это end minus commit. При compaction, транзакциях и редких commit разность не равна числу необработанных бизнес-событий          | Сопоставить разность offset с возрастом события и скоростью потока                                         |
| Ordering                 | Порядок внутри партиции не создаёт глобального порядка topic или порядка завершения параллельной обработки                                        | Изменение числа партиций и маршрутизации ключа рассматривается отдельно                                    |
| Consumer groups          | Одна партиция назначена одному члену обычной группы в текущем назначении. Share groups имеют другую модель                                        | 3 партиции и 5 членов обычной группы: максимум 3 с назначением этого topic                                 |
| auto.offset.reset        | Применяется при отсутствии пригодного offset, а не перематывает существующую группу при каждом старте                                             | При сохранённом offset 800 настройка earliest сама не делает replay                                        |
| Replication / ISR / acks | RF - назначенные копии; ISR - синхронный набор. acks=all учитывает текущий ISR, minISR задаёт нижнюю границу. ELR не моделируется                 | RF=3/minISR=2: при ISR=1 запись с acks=all не засчитывается успешной                                       |
| Producer idempotence     | Защищает предусмотренные протокольные повторы, а не любую повторную бизнес-команду                                                                | Два самостоятельных send одного факта не считаются автоматически одной бизнес-операцией                    |
| KRaft                    | Кворум метаданных и репликация пользовательских партиций решают разные задачи                                                                     | Три контроллера не превращают topic RF=1 в три копии данных                                                |
| Exactly-once             | Kafka-транзакция может связать выходные записи и offset; внешний HTTP-эффект не включается автоматически                                          | Отмена транзакции Kafka не откатывает уже выполненный платёж                                               |
| Retention / compaction   | Delete ограничивает историю; compaction сохраняет последнее состояние ключей постепенно и не перенумеровывает offset                              | Повторное чтение не восстанавливает удалённые события; tombstone отличается от пустой строки               |

Сверено по [KafkaConsumer API](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [Consumer Configs](https://kafka.apache.org/42/configuration/consumer-configs/), [Producer Configs](https://kafka.apache.org/42/configuration/producer-configs/), [Topic Configs](https://kafka.apache.org/42/configuration/topic-configs/), [Confluent Partitions](https://developer.confluent.io/courses/apache-kafka/partitions/), [Confluent Transactions](https://developer.confluent.io/courses/architecture/transactions/), [Confluent Compaction](https://developer.confluent.io/courses/architecture/compaction/). Параметры JVM-клиента в уроках помечены явно; лабораторный адаптер обязан учитывать API своей библиотеки.

## Измеримый quality bar

Таблица задаёт критерии приёмки, а не автоматически подтверждает их выполнение. Фактический статус и команды должны храниться в отдельном отчёте проверки поставки.

| Область              | Критерий                                                                                                                                          | Достаточное свидетельство                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Контент              | 6 модулей, 18 уникальных уроков; 18 вопросов и 18 инженерных ситуаций; для каждого корректный индекс, разбор и официальный источник               | Автоматическая проверка структуры плюс содержательная ревизия спорных гарантий |
| Прогресс             | Неверный ответ не завершает соответствующий этап; результат переживает перезапуск; повторное завершение не удваивает процент                      | Тесты API и проверка сохранённого состояния после нового запуска               |
| Лаборатория          | Успешная отправка и чтение сверяют реальные сообщения; недоступный Docker даёт явную ошибку; приложение принимает только предусмотренные действия | Интеграционный тест настоящего брокера и отрицательные проверки                |
| Границы свидетельств | Каждое отображение модели подписано; HA не объявляется проверенной на одном broker                                                                | Ревизия интерфейса и документации                                              |
| UX                   | Основной путь можно пройти с клавиатуры; видимый focus; ширины 390 и 1440 px не создают непреднамеренный горизонтальный скролл                    | Браузерная проверка и снимки интерфейса                                        |
| Ошибки               | Ошибка сети, сервера или стенда отображается понятным сообщением; повтор действия восстанавливает путь после устранения причины                   | Негативные browser/API-сценарии                                                |
| Поставка             | Чистая установка из lockfile, тесты и production build проходят; локальный запуск возвращает готовый интерфейс                                    | Выполненные команды с итогами, версиями и платформой                           |
| GitHub               | Публичный или разрешённый пользователем репозиторий содержит документацию запуска; Actions выполняются на опубликованном commit                   | Проверенная ссылка на repository и завершённый run для его SHA                 |
| Безопасность         | В репозитории нет локальной БД и секретов; нет произвольных команд из браузера; пути/входы валидируются; локальная сетевая граница описана        | Ревизия diff, отрицательные тесты и фактические настройки прослушивания        |
| Повторяемость        | Образ Kafka имеет явный tag, зависимости - lockfile; данные не уничтожаются обычной остановкой                                                    | Повторный запуск и проверка сохранённого прогресса                             |

## Что потребует следующего исследования

- Проверка программы на учащихся: время первого успеха, причины ошибок, доля завершивших практику и удержание знаний после паузы. Численных результатов этого исследования пока нет.
- Многоброкерный стенд с реальными отказами, потерей ISR, сменой лидера и восстановлением. Модель полезна для объяснения, но не заменяет эти испытания.
- Нагрузочные бюджеты для конкретной среды: одновременные пользователи, размер событий, latency, CPU и память. Локальная поставка не имеет проверенного обещания массовой нагрузки.
- Публичный сервис: отдельные исполнители лабораторий, аутентификация, авторизация, TLS, квоты, сетевые границы, резервирование и восстановление. Эти возможности не следуют из наличия GitHub-репозитория.
- Расширенная практика по schemas, Kafka Connect, CDC и внешнему exactly-once: каждый сценарий требует своего компонента и проверки границы транзакции. [Schema Evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html), [Transactional Outbox](https://developer.confluent.io/courses/microservices/the-transactional-outbox-pattern/).

Основной результат исследования - конкретный объём локального продукта и критерии, по которым можно отличить работающую поставку от красивого прототипа. Фактическая готовность определяется выполненными проверками, а не этим описанием.
